四、实验内容（步骤）

本实验以「校园代拿平台」为分析对象。该平台面向高校在校学生，提供快递代取、外卖代拿、打印排队等校园跑腿任务的发布、撮合、结算与管理服务。系统由原单体工程 demo 演进为基于 Spring Cloud Alibaba 的微服务架构，前端采用 Vue 3 + Vite，后端包含网关、认证、用户、任务、审计、聊天、钱包等七个业务服务，并集成 Nacos 服务发现、Sentinel 限流熔断、Elasticsearch 任务搜索及 Ollama 本地大模型辅助审核等能力。以下按照软件需求开发基本流程，依次完成战略分析、用户识别、需求获取、需求建模与需求定义等工作。

1、战略分析

（1）业务背景与问题陈述

高校校园面积有限但快递点、食堂、文印店分布分散，学生在上课、实验或休息时段常面临「取件排队久、无暇跑腿、信息沟通不畅」等问题。传统线下互助缺乏规范流程与信用约束，易出现任务描述不清、赏金纠纷、失联毁约等情况。因此需要一套面向校园场景的代拿撮合平台，在发布者、接单员与平台管理员之间建立标准化协作机制。

（2）愿景（Vision）

为高校学生提供安全、便捷、可信的校园代拿服务：让有需求的同学快速发布任务并预付赏金，让有闲暇时间的同学通过认证后接单获得收入，平台以审核机制、信誉体系、钱包结算和即时通讯保障交易过程可追踪、可仲裁、可运营。

（3）项目范围

系统范围内包括：用户注册登录（含短信验证码）、个人资料与头像审核、接单员认证申请、任务发布与全生命周期管理、任务大厅浏览与搜索、钱包预付与结算、提现申请与审核、用户间私信及 WebSocket 实时通知、管理员后台（任务/用户/申诉/公告/日志/统计/AI 配置）等。

系统范围外包括：对接微信/支付宝等真实支付通道、跨校区或跨城市配送、骑手实时 GPS 轨迹监控、原生移动 App（当前为 Web 端）。上述排除项可在后续版本中扩展。

（4）约束与假设

① 用户群体为本校注册学生，管理员账号由系统预配置（如 admin、admin2 等）。② 钱包为平台内虚拟余额，用于课程/毕设演示，不涉及真实资金清算。③ 各微服务当前共享 MySQL 数据库 campus_delivery，适合教学演示；生产环境建议按业务域拆库。④ 短信服务依赖阿里云号码认证 API，开发环境可关闭并以模拟验证码联调。⑤ AI 审核依赖本机 Ollama 服务，不可用时不应误驳回任务。

2、识别用户类型

结合愿景与校园业务场景，采用组织结构图与用户角色表识别干系人如下。

（1）系统干系人

① 发布者（普通学生）：有代拿需求，关注发布便捷性、赏金合理性与完成质量。② 接单员（认证学生）：关注可接任务数量、赏金收益与申诉公平性。③ 平台管理员：负责内容审核、用户治理、提现审批与运营公告。④ 外部服务提供商：阿里云（短信）、Ollama（AI 推理）、Nacos/Sentinel/Elasticsearch（基础设施）。

（2）用户角色与权限概览

发布者：注册登录、发布/取消/确认任务、评价、聊天、钱包查询与充值（管理员充入）、提现（若有余额）。接单员：在发布者权限基础上，需通过认证后方可接单、标记完成、发起申诉。管理员：拥有全部后台模块访问权，包括用户启用/禁用、头像与接单员审核、任务通过/驳回、申诉裁决、公告 CRUD、提现审核、钱包充值、AI 配置及操作日志查询。未登录用户仅可访问登录注册相关接口。

（3）过程产物

本步骤输出《用户角色表》《干系人分析表》及《组织结构图》（学校—平台—用户三层），明确各角色与系统的交互边界，为后续用例建模提供参与者清单。

3、需求获取

（1）获取方法

本实验综合采用以下需求获取手段：① 用户访谈（模拟）：针对 5~8 名同学进行半结构化访谈，了解取快递频率、可接受赏金区间、对实名认证与信誉分的态度。② 竞品分析：参考 UU 跑腿、闪送校园版等产品的任务发布、订单状态与评价机制。③ 现有系统逆向分析：对本项目 campus-cloud 源码、README、联调说明及数据库实体进行梳理，提取已实现功能与隐含业务规则。④ 焦点小组讨论（模拟）：讨论「超时任务如何处理」「申诉是否影响接单员完成率」等争议点并形成结论。

（2）需求清单（节选）

功能需求：F01 短信/密码注册登录；F02 接单员实名申请与审核；F03 多类型任务发布与地图选点；F04 任务大厅筛选与 ES 搜索；F05 接单与状态流转；F06 钱包预付赏金与完成结算；F07 提现申请与管理员审核；F08 私信与 WebSocket 推送；F09 管理员审核任务/用户/申诉；F10 AI 辅助内容审核；F11 公告发布与展示；F12 管理统计看板（ECharts）。

非功能需求：NF01 JWT 统一鉴权；NF02 Gateway 单入口；NF03 Sentinel 熔断降级；NF04 单点登录与会话踢下线；NF05 操作审计日志；NF06 待确认任务 30 分钟自动确认；NF07 信誉分默认 80 及封禁策略。

数据需求：用户、任务、聊天、钱包账户、钱包流水、提现申请、公告、短信验证码、管理员日志等实体及其关联关系。

4、需求分析与建模

根据需求清单，按业务需求、用户需求、业务规则、功能需求、质量属性、约束、外部接口及数据需求等类型归类整理，并采用 UML 及结构化工具建模如下。

（1）用例建模

识别出发布者、接单员、管理员三个主要参与者，绘制系统总体用例图。核心用例包括：用户注册（UC_001）、用户登录（UC_002）、接单员申请（UC_003）、发布任务（UC_004）、浏览搜索大厅（UC_005）、接单（UC_006）、完成与确认结算（UC_007）、提现申请（UC_008）、管理员审核任务（UC_009）、私信聊天（UC_010）等。各用例均编写用例规约表，明确前置条件、基本流程、异常流程及补充说明（详见附件《十个用例表》）。

（2）活动图与顺序图

绘制「发布并完成代拿任务」活动图：发布者填写任务→钱包扣款→待审核→（AI/人工）审核通过→大厅展示→接单员接单→配送完成→待确认→结算→评价。绘制「发布任务」顺序图：涉及前端、Gateway、task-service、wallet-service（Feign 扣款）、audit-service（写日志）、chat-service（推送）等对象的交互时序。

（3）状态机建模

配送任务（delivery_task）是状态变化最复杂的实体，共 8 种状态：PENDING_REVIEW、REJECTED、OPEN、CLAIMED、OVERDUE、PENDING_CONFIRMATION、COMPLETED、CANCELLED。绘制状态机图并编制状态转换表，明确各迁移触发条件（如管理员 approve、接单 claim、超时 overdue、发布者 confirm 等），保证任务生命周期无二义性。

（4）数据建模

采用 E-R 图描述 user_account、delivery_task、wallet_account、wallet_transaction、wallet_withdraw_request、chat_message、notice、admin_operation_log 等实体及其一对多、一对一关系。编制五张核心表数据字典（user_account、delivery_task、chat_message、wallet_account、wallet_withdraw_request），逐字段定义数据类型、空值约束、默认值及业务含义（详见附件《五张数据字典全字段版》）。任务 status、提现 status、流水 type 等字段采用枚举约束并在字典中列出允许值。

（5）用户权限矩阵

以「功能模块 × 角色」矩阵标注权限：例如「发布任务」仅登录用户；「接单」仅 rider_approved=true 用户；「审核任务」仅 admin 白名单用户；「内部接口 /internal/**」仅服务间 Feign 调用。矩阵与 Gateway 路由规则、AdminPolicy 校验逻辑保持一致。

（6）非功能需求归纳

安全性：JWT + Gateway 鉴权、密码加密、管理员白名单、内部接口不对外暴露。性能与可用性：Sentinel 对 Feign 与网关路由配置熔断；ES 搜索可选；WebSocket 降低轮询压力。易用性：大厅筛选、Leaflet 地图选点、实时 Toast 提醒。可扩展性：微服务按域拆分，Nacos 注册，Sentinel 规则持久化至 Nacos。互操作性：REST + WebSocket；对接阿里云短信与 Ollama HTTP API。

5、需求定义

（1）需求质量特征检验

对需求集合逐条审查：① 完整性：覆盖注册、任务、钱包、聊天、管理五大域及主要异常分支。② 无二义性：任务状态枚举、角色权限、赏金结算规则均以表格或状态机明确定义。③ 正确性：需求描述与 campus-cloud 现有实现及数据库 schema 一致，可通过接口联调验证。④ 必要性：剔除真实支付、GPS 追踪等范围外需求，避免镀金。⑤ 可追溯性：每条功能需求 F01~F12 可映射至对应用例 UC_xxx 及后端 Controller/Service。⑥ 一致性：前端 admin 白名单与后端 app.admin.usernames 配置一致；Gateway 路由与服务名一致。

（2）输出成果

本阶段最终输出《校园代拿平台软件需求规格说明书》（见本报告「五、结果分析」），并附用例规约表、状态转换表、数据字典、用例图、活动图、顺序图、状态机图、E-R 图及用户权限矩阵等建模产物。上述文档将作为后续详细设计、编码实现与测试验收的基准，并支持需求变更时的版本管理与影响分析。

（3）需求确认

需求分析结果已与指导教师及项目组（同组人员：无）进行走查确认：核心业务闭环「发布—审核—接单—完成—结算—评价」定义清晰；管理员治理与申诉仲裁机制满足平台运营需要；非功能需求与微服务架构技术选型相匹配。后续若扩展真实支付或拆库部署，需通过变更控制流程更新本需求基线。
